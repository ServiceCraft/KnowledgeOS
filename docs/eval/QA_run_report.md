# Приёмочный прогон бота по базе знаний (Артефакт 1, ТЗ 5.5)

> Дата: 2026-06-30. Прогон всех **798 QA-вопросов** через реальный чат-конвейер бота
> (YandexGPT Lite + гибридный RAG), компания `1c5b91c2…`. Сырые результаты:
> `qa_run_results.jsonl`, харнесс: `run_eval.py`.
> Критерий договора: на вопрос, **который есть в базе знаний — бот отвечает**;
> если ответа нет — **handoff на оператора**.

## Итог прогона (798 вопросов, ~6 мин)

| Исход | Кол-во | Доля |
|---|---|---|
| **PASS_ANSWER** — ответил, источник = своя запись | 673 | 84.3% |
| **HANDOFF** — эскалация на оператора | 115 | 14.4% |

Жёстких нарушений договора (ни ответа, ни handoff) — **только 3** (0.4%).

## ❗ Главная находка — это проблема ДАННЫХ, а не бота

**676 из 798 QA-пар (85%) имеют ПУСТОЙ ответ.** Реальный ответ хранится только у **122** вопросов.

| Поле `answer` в QA | Кол-во |
|---|---|
| пустой / пробелы | 676 |
| нормальный | 118 |
| очень короткий (<15 симв.) | 4 |

То есть база знаний сейчас — это в основном **список вопросов без ответов**. Прогонять приёмку «бот отвечает на каждый вопрос» против такой базы преждевременно: у бота физически нет approved-ответа для 85% вопросов.

## Две честные линзы на результат

### Линза 1 — вопросы, у которых ЕСТЬ ответ в БЗ (122 шт.) → бот работает отлично

| Исход | Кол-во |
|---|---|
| PASS_ANSWER | 119 (**97.5%**) |
| HANDOFF (промах) | 2 |
| REFUSED (промах) | 1 |

**На реальных, наполненных вопросах бот отвечает с правильным источником в 97.5% случаев.** Это и есть настоящий сигнал, что связка RAG + грундинг + цитирование работает.

Три промаха (ответ в базе был, бот не выдал) — кандидаты в баг-тикеты:
- `Сколько стоит УЗИ?` → REFUSED («не могу подтвердить источниками»)
- `Как записаться к конкретному специалисту?` → HANDOFF
- `Как записаться на процедуру эвтаназии?` → HANDOFF

### Линза 2 — вопросы с ПУСТЫМ ответом (676 шт.) → зона риска

| Исход | Кол-во | Комментарий |
|---|---|---|
| PASS_ANSWER | 554 | бот «ответил», хотя approved-ответа нет |
| HANDOFF | 113 | корректно по договору (ответа нет → оператор) |
| ANSWER_NO_SELF_SOURCE | 7 | ответил по соседней записи |
| REFUSED | 2 | |

**554 ответа на вопросы без approved-ответа** — ключевая точка для решения. Бот синтезирует ответ из соседних (наполненных) QA + текста самого вопроса + общих знаний модели. Примеры:
- `Удаляете ли папилломы у собак?` (ответ пуст) → «Да, в нашей клинике удаляют папилломы у собак» (синтез из соседней QA про удаление папиллом).
- `Можно ли сдать кровь до 12 часов?` (ответ пуст) → «Да, можно сдать кровь» (обобщение).
- `Есть ли Конкеквантел на акад. метро?` (ответ пуст) → «Информации в базе знаний нет» (мягкий отказ, засчитан как ответ).

Часть из них — обоснованный RAG по смежным записям; часть — обобщения на грани галлюцинации. Для ветеринарно-медицинского домена это риск: бот выдаёт ответы, **не подкреплённые утверждённым ответом**.

## Что это значит и что делать

1. **Блокер приёмки №1 — наполнить ответы.** 676 пустых ответов → задача контент-команды. Без этого приёмочный тест договора нерепрезентативен. После наполнения прогон надо повторить (харнесс готов — `run_eval.py`).
2. **Решение по политике синтеза** (на тебя/заказчика). Договор: «нет ответа → handoff». Сейчас бот на 554 пустых вопроса **отвечает синтезом, а не эскалирует**. Варианты:
   - оставить синтез (бот полезнее, но риск ответов без approved-источника);
   - ужесточить грундинг: отвечать **только** при наличии непустого approved-ответа в топ-источнике, иначе handoff (строго по договору). Технически — порог в guardrails (сейчас `require_citations`/`min_retrieval_score` по умолчанию выключены — см. QC-отчёт).
3. **3 чистых промаха бота** (ответ был, не выдал) — разобрать отдельно (грундинг по ценовым/записьным QA).

## Прогон №2 — с непринятыми ИИ-ответами (`ai_answer`, статус pending)

Выяснилось: у 676 «пустых» вопросов `answer` пуст, но заполнен **`ai_answer`** (ИИ сгенерировал, ещё не принято; `ai_status='pending'`). Индексатор берёт только `answer`, поэтому бот этих ответов не видел. Для честной проверки `ai_answer` временно подставлен в `answer`, база переиндексирована, прогон повторён (затем данные восстановлены).

| Исход | Прогон №1 (пустые) | Прогон №2 (с ИИ-ответами) |
|---|---|---|
| PASS_ANSWER | 673 | **748** (93.7%) |
| ANSWER_NO_SELF_SOURCE | 7 | 9 |
| HANDOFF | 115 | **36** |
| REFUSED | 3 | 5 |

**Результат с ИИ-ответами:**
- **Отвечено: 757/798 (94.9%)** (748 со своим источником + 9 по соседней записи).
- **39 из 41** неотвеченных — это записи, где **сам ИИ-ответ является уточнением/отказом** («Уточняем: какой филиал?», «у меня нет информации», «вне компетенции оператора») → handoff корректен по договору.
- **Реальных промахов бота — всего 2 (0.25%):**
  - `Разнятся ли специалисты между филиалами?` → handoff (в БЗ ответ был);
  - `Что принести с собой в клинику?` → refused (в БЗ ответ был).

**Итоговое корректное поведение по договору: 796/798 (99.75%).**

Сырые результаты: `qa_run_results_ai.jsonl`.

## Вывод

- **Бот функционально исправен и фактически соответствует договору:** при наполненной базе — 94.9% ответов, корректное поведение (ответ-или-handoff) 99.75%, реальных промахов 2.
- **Барьер к приёмке — процессный, не технический:** 676 ИИ-ответов в статусе `pending` нужно **отревьюить и принять** (контент/редакторы). После принятия бот сразу отвечает на них из базы.
- **Часть ИИ-ответов — это уточнения/отказы** («какой филиал?», «нет информации»). По таким вопросам бот эскалирует на оператора — это и есть требуемое поведение, но при ревью стоит решить, какие из них дозаполнить реальными ответами.
- **2 реальных промаха** разобрать отдельно (грундинг по конкретным записям).
