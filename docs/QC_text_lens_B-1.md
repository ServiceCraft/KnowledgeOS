## Критические и major-находки (приоритет на доработку)

### Б3 — Ядро чата

1. **[MAJOR] Стриминг не реально инкрементальный.** `runSingle` (`service/chat.go:507-525`) собирает весь ответ LLM в буфер, затем `emitAnswer` (`service/chat.go:740-759`) шлёт один `delta`-event с полным текстом. Frontend (`BotPlaygroundPage.tsx:199-205`) игнорирует `delta`/`sources`/`usage`, ждёт `message`. Сделано намеренно (guardrails проверяют ответ целиком), но **критерий приёмки Б3 «стриминг по мере генерации» не выполнен**. Нужно либо согласовать с заказчиком новую формулировку (streaming после guardrail-проверки), либо реализовать токен-стриминг с пост-фильтрацией.
2. **[MAJOR] Сиротское user-сообщение при ошибке LLM.** `prepareTurn` (`service/chat.go:268`) сохраняет сообщение пользователя в БД до `generate()`. При падении LLM/retriever ответа нет, при повторе появляется второй user-message — история ломается. Нужен rollback/компенсация.
3. **[MAJOR] `context.WithoutCancel` в HTTP-горутине** (`handler/chat.go:116`). `StreamMessage` выполняется синхронно; при дисконнекте клиента горутина висит до конца генерации (30–60 с). Под пиковой нагрузкой — накопление заблокированных горутин.
4. **[MINOR] Нет `X-Accel-Buffering: no`** (`handler/chat.go:108-111`). За nginx SSE будет буферизоваться — события не дойдут до закрытия соединения. Нужен заголовок или `proxy_buffering off`.
5. **[MINOR] Token budget — символьный, не токеновый** (`chatHistoryMaxRunes=12000`, `service/chat.go:947`). Для кириллицы риск выхода за контекст-окно.

### Каналы

6. **[CRITICAL/проверить на e2e] VK-авторегистрация webhook не соответствует VK API.** `vk/adapter.go:36-67` шлёт `POST` на произвольный URL с Bearer; реальный VK требует `groups.addCallbackServer` + `groups.setCallbackSettings`. Без кастомного прокси VK-канал может не подняться. **Проверить на реальной группе VK.**
7. **[MAJOR] Нет дедупликации `update_id`** (`gateway.go:87-156`). `update_id` парсится, но не хранится. При повторной доставке (TG/MAX перепосылают без 200) — повторный вызов LLM и дубль ответа.
8. **[MAJOR] `NotifyHandoff` жёстко через Telegram** (`gateway.go:181`) независимо от канала сессии. Клиент из VK/MAX → уведомление уходит в TG; если TG не настроен — теряется молча.
9. **[MINOR] Sources не доходят до пользователя в канале.** Все 3 адаптера игнорируют `msg.Sources` в `SendMessage`. В БД источники есть (критерий «фиксируются» выполнен), но в сообщение клиенту не попадают.
10. **[MINOR] MAX/VK не маппят вложения**; VK `random_id` через `math/rand`; MAX — неполное тестовое покрытие.

### Б1 / Б2

11. **[MAJOR] Нет батчинга эмбеддингов** (`llm/yandex/client.go:190-215`). `embed()` шлёт N последовательных одиночных HTTP-запросов. ТЗ требует батчинг — при индексации тысяч чанков лавина запросов. Ретраи/backoff при этом реализованы корректно.
12. **[MAJOR] Чат падает 400 без tenant-secret и без `SECRETS_ENCRYPTION_KEY`** (`llm_factory.go:78-97`). Нет поля для глобального IAM-токена через env — режим «только env» не поддержан.
13. **[MAJOR/смягчено] Жёсткая `vector(256)`** (`013_pgvector.sql:15`). Совпадает с Yandex embeddings v2 — в проде работает, но столбец `dim` создаёт ложную видимость динамической размерности; смена модели сломает индекс.
14. **[MAJOR] Первичная индексация только ручная** (POST `/admin/bot/rag/reindex`) + лимит `10000` записей. На свежем деплое индекс пуст до ручного запуска; крупная БЗ индексируется не полностью.
15. **[MAJOR] Ошибки `ScheduleUpsert/Delete` игнорируются** (`article.go:80`, аналогично qa/pricing): `_ = s.indexer.Schedule...`. Сбой постановки в очередь теряется молча — запись не попадёт в индекс.

> RRF реализован **корректно** (`score += 1/(60+rank)`, k=60 — стандарт), автоиндексация — через асинхронную очередь с retry/backoff, изоляция `company_id` соблюдена везде. Это сильная часть.

### Б5 — Guardrails

16. **[MAJOR] Все опциональные пороги по умолчанию выключены** (`016_chat_guardrails.sql:31-41`): `min_confidence=0`, `min_retrieval_score=0`, `escalate_on_low_confidence=false`, `require_citations=false`. Новый тенант защищён только тремя hardcoded-правилами (no_context / fabricated citation / prompt_leak).
17. **[MAJOR] Prompt-injection — только на выходе** (`guardrails.go:196-215`). Предобработки входа нет; `leakMarkers` содержат хардкод «администратор колл-центра» (не переносимо между вертикалями).
18. **[MAJOR] ПДн-редактирование узкое.** `privacy.Redact` вызывается в одной точке (лог tool-ошибок, `chat.go:617`), покрывает только email/телефон. Контент сообщений в БД не маскируется.

> Сильная часть Б5: grounding-отказ при пустом KB реален; fabricated-citation детектируется верифицируемо (сравнение ID); confidence — прозрачная эвристика; автоэскалация подключена; eval-харнес формирует реальный JSON/Markdown отчёт.

### Б4 / Handoff

19. **[MAJOR] Маскирование ошибок БД** в `get_service_info.go:85,91,98` — при недоступности БД оператор видит «article not found» вместо 500.
20. **[MINOR/perf] Нет индекса `(company_id, state)`** на `chat_sessions` (есть `company_last_message`, `company_channel_external`). Очередь эскалаций поллит каждые 4–5 с → full scan под нагрузкой.
21. **[вопрос] Роль `editor` исключена из handoff-роутов** (`router.go:175`: только `viewer/admin/superadmin`). Вероятно осознанно (viewer = «оператор» по ТЗ), но стоит подтвердить.

> Сильная часть Handoff: FSM корректна, «взять диалог» **атомарен** (`UPDATE ... WHERE state IN (...)` + проверка `RowsAffected`, тест `TestHandoffServiceClaimIsAtomic`), бот реально молчит у оператора, tool-пайплайн эскалации замкнут.

## Безопасность секретов — отдельно

Реализация AES-256-GCM **корректна**: уникальный nonce (`crypto/rand`), хранится отдельно от шифртекста, `normalizeKey` принимает base64/hex/raw с SHA-256 fallback, тест на уникальность nonce есть. Открытые ключи/токены **не попадают в логи** (логируются только `kind`, `company_id`, `auth_type`). Критических секьюрити-дефектов по секретам не обнаружено.
