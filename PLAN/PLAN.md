# План реализации модуля «Текстовая линза» (диалоговый ИИ-ассистент)

> Источники: `КП_KnowledgeOS_текст-линза-итог.docx`, `ТЗ_KnowledgeOS-текст-линза-итог.docx` (от 16.06.2026).
> Документ описывает **gap** между текущим состоянием платформы и требованиями ТЗ, и план работ по блокам ТЗ (Б1–Б5 + модули).
> Приёмка идёт по критериям ТЗ — структура плана повторяет структуру ТЗ, чтобы трассировка была однозначной.

## 0. Краткое резюме (gap)

Текущая платформа KnowledgeOS — это **система управления базой знаний**: статьи, QA-пары, прайс-дерево, темы, звонки/транскрипты, комментарии, связи, пользователи/роли, мультитенантность, синхронизация local↔cloud, экспорт/импорт, бэкап. Стек: Go + Chi + GORM + PostgreSQL 16, React + TS + Vite + shadcn/ui, Docker/Nginx.

Модуль «Текстовая линза» — **полностью новый функционал**. На текущий момент **отсутствует всё ядро бота**:

| Требуется по ТЗ | Сейчас в системе | Статус |
|---|---|---|
| LLM-провайдер (YandexGPT: чат, стриминг, tools) | нет интеграции с LLM | ❌ нет |
| Эмбеддинги + pgvector + векторный/гибридный поиск (RRF) | только pg_trgm + неиспользуемый tsvector | ❌ нет (есть только триграммы) |
| Диалоги/сообщения (домен, миграции, история) | нет сущностей чата | ❌ нет |
| Оркестратор RAG-диалога + персона + Chat REST API + SSE | нет | ❌ нет |
| Фреймворк вызова инструментов (tools) | нет | ❌ нет |
| Guardrails / grounding / цитирование / отказ | нет | ❌ нет |
| Каналы Telegram / MAX / VK (вебхуки) | нет | ❌ нет |
| Handoff на оператора (FSM, очередь, перехват) | нет; роль `viewer` ≈ «Оператор», но без логики | ❌ нет |
| Интеграция Bitrix24 (провайдер действий) | нет | ❌ нет |
| Пер-тенантные настройки бота + шифрование секретов в БД | только `Company.name/tier`; ключи — хэши/`env`, не шифр. секреты | ❌ нет |
| Плейграунд бота в админке | нет | ❌ нет |
| Метрики диалогов (отвечено/эскалировано/токены/стоимость) | нет | ❌ нет |

**Что переиспользуется как фундамент (✅ уже есть):**
- Мультитенантность (`company_id` во всех сущностях, `middleware/tenant.go`).
- Аутентификация JWT + refresh + API-ключи (`internal/auth`, `middleware/auth.go`).
- Ролевая модель: `superadmin / admin / editor / viewer` (`domain/user.go`, `middleware/role.go`, `lib/roles.ts`).
- Паттерн слоёв `domain → store → service → handler` + Chi-роутер (`handler/router.go`).
- Инфраструктура миграций (`internal/database/migrate.go`, `migrations/NNN_*.sql`).
- База знаний как источник RAG: `Article`, `QAPair`, `PricingNode`, `Theme` + изоляция по компании и темам.
- Триграммный поиск (`004_trigram.sql`, `store/search.go`) — войдёт как одна из веток гибридного ретривера.
- Существующая админка React (Vite, shadcn/ui), сайдбар, query-слой (`hooks/`, `api/`).
- Docker-compose / Nginx — деплой единым бэкендом (новый модуль внутри существующего бэкенда, отдельного сервиса не требуется).

**Объём по ТЗ:** обязательная база Б1–Б5 = **93 SP**; модули: каналы (пакет), handoff = **16 SP**, Bitrix24 (этап 2) = **31 SP**.

## Этап 1 — Бот

### Б1. Фундамент: провайдер-абстракция и конфигурация тенанта (16 SP)

**Gap:** нет ни LLM-клиента, ни таблицы настроек тенанта, ни шифрования секретов.

**Что сделать:**
- [ ] Пакет `internal/llm`: интерфейс `Provider` (`Chat(ctx, messages, tools) (Response, error)`, `ChatStream(...) (<-chan Chunk, error)`, поддержка tool-calls) + интерфейс `Embedder` (`Embed(ctx, []string) ([][]float32, error)`).
- [ ] Адаптер `internal/llm/yandex`: реализация `Provider` и `Embedder` поверх YandexGPT / YandexGPT Embeddings (Yandex Cloud Foundation Models REST), с батчингом и ретраями (экспоненциальный backoff).
- [ ] Конфиг провайдера: расширить `internal/config/config.go` (Yandex folder-id, IAM/API-key endpoint) **как дефолт**, но фактический выбор модели/ключей — на уровне тенанта.
- [ ] Миграция `011_bot_settings.sql`: таблица `bot_settings` (one-to-one с `companies`): `model` (Lite/Pro), параметры генерации (temperature, max_tokens), персона (имя/тон/правила — для Б3), вкл/выкл модулей. Переключение Lite↔Pro из админки без участия исполнителя.
- [ ] Миграция `012_tenant_secrets.sql`: таблица `tenant_secrets` (`company_id`, `kind` — `llm`/`telegram`/`max`/`vk`/`bitrix24`, `ciphertext`, `nonce`). **Шифрование в БД** (AES-GCM), мастер-ключ из `env` (`SECRETS_ENCRYPTION_KEY`). Пакет `internal/crypto` (encrypt/decrypt). В логах и БД — никогда в открытом виде.
- [ ] CRUD-эндпоинты настроек бота и секретов (admin+), форма в админке (раздел «Настройки → Бот»).

**Критерии приёмки (ТЗ 5.1):** вызов LLM и эмбеддингов работает через YandexGPT; настройки/ключи задаются для конкретной компании; ключей нет в БД/логах в открытом виде.

### Б2. Ретривер RAG: векторный + гибридный поиск (22 SP)

**Gap:** есть только триграммный поиск по QA/Article; pgvector, эмбеддинги, конвейер индексации и RRF — отсутствуют.

**Что сделать:**
- [ ] Миграция `013_pgvector.sql`: `CREATE EXTENSION vector`; таблица `kb_embeddings` (`company_id`, `entity_type`, `entity_id`, `chunk_idx`, `content`, `embedding vector(N)`, `model`, `dim`) — модель и размерность фиксируются рядом с вектором. Векторный индекс (HNSW/IVFFlat).
- [ ] Конвейер индексации `internal/rag/indexer`: первичная индексация существующей базы знаний; **автообновление эмбеддингов** при создании/изменении `Article`/`QAPair`/`PricingNode` (хук в соответствующих service-методах или очередь/воркер); разбиение длинных статей на фрагменты (chunking).
- [ ] Гибридный ретривер `internal/rag/retriever`: объединение векторного поиска (pgvector) и текстового/триграммного (переиспользуя `store/search.go`) методом **Reciprocal Rank Fusion**; изоляция по `company_id` и фильтр по темам.
- [ ] Препроцессинг запроса: переформулирование разговорной фразы клиента в поисковый запрос средствами LLM (вызов `Provider`).

**Критерии приёмки (ТЗ 5.2):** разговорные формулировки находят релевантные записи, которые не находит чисто текстовый поиск; новые/изменённые записи попадают в индекс автоматически; данные компаний изолированы.

### Б3. Ядро чата — «линза» (34 SP)

**Gap:** нет доменной модели диалогов, оркестратора, персоны, Chat API и стриминга.

**Что сделать:**
- [ ] Миграция `014_chat.sql`: `chat_sessions` (`company_id`, `channel`, `external_chat_id`, `state`, `operator_id`, timestamps) и `chat_messages` (`session_id`, `role` — user/assistant/tool/operator, `content`, `tool_calls` JSONB, `sources` JSONB, `tokens_prompt/tokens_completion`). Домен `internal/domain/chat.go`, store/service по существующему паттерну.
- [ ] Оркестратор `internal/chat/orchestrator`: пайплайн **извлечение контекста (Б2) → сборка промпта → вызов LLM (Б1) → обработка tool-calls (Б4) → ответ**; управление историей и обрезкой контекста (token budget).
- [ ] Персона «администратор колл-центра»: системный промпт из `bot_settings` (тон/имя/правила), подстановка прайса и услуг из базы знаний.
- [ ] **Chat REST API** (`handler/chat.go`, новые маршруты в `router.go`): создать сессию, отправить сообщение, получить историю; **стриминг ответа через SSE**.
- [ ] Маршруты бота: внутренние (для плейграунда, JWT) и публичные (для каналов — см. модуль каналов, с верификацией вебхуков).
- [ ] **Плейграунд** в админке (страница «Бот → Плейграунд»): чат-интерфейс поверх Chat API + SSE; виден список источников ответа. (Артефакт «доступен во внутреннем плейграунде».)

**Критерии приёмки (ТЗ 5.3):** многоходовой диалог с сохранением истории через REST API; ответы опираются на извлечённый контекст; стриминг отдаёт ответ по мере генерации.

### Б4. Фреймворк вызова инструментов (8 SP)

**Gap:** отсутствует полностью.

**Что сделать:**
- [ ] Пакет `internal/chat/tools`: регистр инструментов, JSON-schema описаний, диспетчер, валидация аргументов; интеграция tool-calls в цикл оркестратора (Б3).
- [ ] Инструменты базы знаний: `search_knowledge` (поиск по знаниям через Б2), `get_pricing` (прайс), `get_service_info` (информация об услуге).

**Критерии приёмки (ТЗ 5.4):** бот сам вызывает поиск по базе знаний и прайсу и использует результаты; некорректные аргументы отклоняются валидацией.

### Б5. Guardrails / защита от галлюцинаций (13 SP)

**Gap:** отсутствует полностью.

**Что сделать:**
- [ ] Grounding и цитирование: ответ строится только на извлечённом контексте; к ответу прикрепляются источники (`sources` в `chat_messages`); при отсутствии данных — корректный **отказ** (не «выдумывать»).
- [ ] Фильтр тем и безопасность: ограничение тематики, защита от prompt-injection, базовая обработка ПДн.
- [ ] **Скоринг уверенности** ответа с переходом в fallback; при подключённом модуле handoff — **автоэскалация** на оператора.
- [ ] Артефакт-инфраструктура: тестовый прогон по набору внутридоменных вопросов (Артефакт 1) и провокационных/внедоменных (Артефакт 2) — скрипт/харнесс, формирующий отчёт.

**Критерии приёмки (ТЗ 5.5):** на провокационных/внедоменных вопросах бот отказывается или эскалирует; каждый содержательный ответ снабжён источниками из базы знаний.

### Модуль: Каналы — Telegram + MAX + VK (пакет)

**Gap:** отсутствует полностью. Зависит от Б3.

**Что сделать:**
- [ ] Общий слой `internal/channels`: интерфейс шлюза (приём входящего обновления → Chat API → отправка ответа), привязка сессии к чату канала, хранение токенов в `tenant_secrets` (Б1, шифрование).
- [ ] **Telegram**: webhook-эндпоинт с верификацией (secret token), маппинг updates на Chat API, индикация набора текста (`sendChatAction`), привязка сессии к chat_id; токен бота — на уровне тенанта.
- [ ] **MAX**: подключение через Bot API мессенджера MAX (webhook/long-poll), верификация, маппинг сообщений и вложений; токен — на уровне тенанта.
- [ ] **VK**: сообщество через Callback API / Bots Long Poll, верификация (confirmation/secret), маппинг входящих; ключи сообщества — на уровне тенанта.
- [ ] Публичные маршруты вебхуков в `router.go` (без JWT, с верификацией каждого канала).

**Критерии приёмки (ТЗ 6.1):** клиент ведёт полноценный диалог в каждом из трёх каналов; сессия/история сохраняются; источники фиксируются.

### Модуль: Передача живому оператору — handoff (16 SP)

**Gap:** отсутствует. Роль `viewer` («Оператор») есть, но без логики диалога. Зависит от Б3, Б5.

**Что сделать:**
- [ ] **Машина состояний** диалога: `bot → ожидание оператора → оператор → решено`; триггеры: низкая уверенность (Б5), вопрос вне базы знаний, явная просьба клиента, инструмент эскалации (tool в Б4). Состояние в `chat_sessions.state`.
- [ ] **Очередь эскалаций** в админке: список ожидающих, кнопка «взять диалог», ответы от лица оператора (роль `viewer`/оператор получает права на отправку сообщений в назначенный диалог), уведомления (в т.ч. в Telegram-группу).
- [ ] **Маршрутизация:** пока диалог у оператора — бот молчит; по завершении диалог возвращается боту.
- [ ] Фронт: страница «Диалоги / Эскалации» + интерфейс оператора; расширить права роли `viewer` для работы с назначенными диалогами (правка `lib/roles.ts`, `middleware/role.go`).
- [ ] Артефакт «тестовый прогон по handoff».

**Критерии приёмки (ТЗ 6.2):** вопросы вне базы знаний и явная просьба клиента гарантированно переходят на оператора; оператор перехватывает и завершает диалог.

# Best practices: RAG и Guardrails для «Текстовой линзы»

> Для разработчика. Привязано к стеку KnowledgeOS (Go + Chi + GORM + PostgreSQL 16, YandexGPT) и к блокам плана: **Б2 (ретривер)** и **Б5 (guardrails)**. Это не общая теория — это конкретные решения, которые мы принимаем, и грабли, на которые не надо наступать.

---

## Часть 1. RAG

### 1.1. Главное правило, с которого всё начинается

YandexGPT Embeddings v2 — это **две разные модели**, и их нельзя путать:

- `emb://b1gi8ce8tfch6gph82sk/text-embeddings-v2-doc/latest` — векторизуем **то, что кладём в индекс** (статьи, QA, прайс).
- `emb://b1gi8ce8tfch6gph82sk/text-embeddings-v2-query/latest` — векторизуем **поисковый запрос клиента**.

Если проиндексировать базу `query`-моделью или искать `doc`-моделью — формально всё работает, цифры считаются, но релевантность тихо деградирует и поймать это на глаз тяжело. Зашиваем выбор модели в адаптер по типу операции, а не «одна модель на всё».

```go
// internal/llm/yandex
const (
    embModelDoc   = "emb://%s/text-embeddings-v2-doc/latest"   // индексация
    embModelQuery = "emb://%s/text-embeddings-v2-query/latest" // запрос
)

func (y *Yandex) EmbedDocs(ctx context.Context, texts []string) ([][]float32, error)  // doc-модель
func (y *Yandex) EmbedQuery(ctx context.Context, text string) ([]float32, error)        // query-модель
```

Параметры, которые надо знать:
- **Размерность — 256** по умолчанию (у новой v2 настраивается 128–768). Берём дефолт `vector(256)`, но `model` и `dim` храним рядом с вектором (как в плане) — чтобы при смене модели не было «молчаливого» рассинхрона.
- **Вход — до 2048 токенов** на один эмбеддинг. Это жёсткий потолок размера чанка.
- Метрика близости — **косинус** (`vector_cosine_ops`).
- Эндпоинт Foundation Models, авторизация по API-ключу сервисного аккаунта (роль `ai.languageModels.user`).

### 1.2. Чанкинг — по сущностям, а не по символам

У нас структурированная база (`QAPair`, `Article`, `PricingNode`), а не свалка PDF. Поэтому **не режем тупым окном по N символов**. Стратегия по типу:

| Сущность | Что эмбеддим | Что отдаём в контекст LLM |
|---|---|---|
| `QAPair` | текст вопроса (можно вопрос+ответ) | ответ целиком |
| `Article` | абзацы/секции по заголовкам, ~800–1500 симв., overlap ~15% | найденный фрагмент + ссылка на статью |
| `PricingNode` | узел, отрендеренный в естественный текст («Стерилизация кошки — 3500 ₽, …») | тот же рендер |

Почему так: вопрос клиента семантически ближе к **вопросу** из QA-пары, чем к ответу — поэтому эмбеддим вопрос. Прайс в виде дерева плохо ложится в вектор — рендерим в человеческую фразу шаблоном и эмбеддим её. Длинные статьи бьём по смысловым границам (заголовки/абзацы), с небольшим перекрытием, чтобы не рвать мысль на стыке.

Один чанк = одна строка в `kb_embeddings` с `entity_type` / `entity_id` / `chunk_idx` — чтобы из найденного вектора однозначно собрать ссылку на источник (это понадобится в guardrails).

### 1.3. pgvector: индекс и изоляция

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE kb_embeddings (
    id          BIGSERIAL PRIMARY KEY,
    company_id  BIGINT NOT NULL,
    entity_type TEXT   NOT NULL,        -- article | qa | pricing
    entity_id   BIGINT NOT NULL,
    chunk_idx   INT    NOT NULL,
    content     TEXT   NOT NULL,        -- что реально пойдёт в контекст
    content_hash TEXT  NOT NULL,        -- для пропуска неизменённого при реиндексации
    embedding   vector(256) NOT NULL,
    model       TEXT   NOT NULL,
    dim         INT    NOT NULL,
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- HNSW: лучше recall и без шага обучения; важно для инкрементальных вставок
-- (мы реиндексируем по факту правки записи в базе знаний).
CREATE INDEX ON kb_embeddings USING hnsw (embedding vector_cosine_ops);
CREATE INDEX ON kb_embeddings (company_id, entity_type, entity_id);
```

- **HNSW, не IVFFlat.** IVFFlat требует обучающую выборку и плохо живёт с постоянными вставками. У нас база правится редактором → инкрементальная индексация → HNSW.
- **Мультитенантность.** Поиск всегда `WHERE company_id = $tenant`. Фильтр + ANN-индекс в Postgres могут «недобирать» кандидатов: либо переборщить top-k (взять `k * 4` и отфильтровать), либо опираться на iterative index scans pgvector 0.8+. Для масштаба одной клиники (тысячи записей, не миллионы) это не больно, но в код заложить надо сразу.
- `ef_search` — тюним на запросе (recall vs latency), не хардкодим намертво.

### 1.4. Конвейер индексации (Б2) — асинхронно

Эмбеддинг — это сетевой вызов к Yandex. **Нельзя** блокировать им запрос редактора, который просто сохранил статью.

- Хук в service-методах `Create/Update/Delete` для `Article`/`QAPair`/`PricingNode` → кладём задачу в очередь (таблица-джоб или буферизированный канал + воркер).
- Воркер: считает `content_hash`, **пропускает неизменённое**, батчит тексты в один вызов `EmbedDocs`, ретраит с экспоненциальным backoff.
- **Не забыть delete**: удалили запись в базе — удаляем её вектора. Иначе бот цитирует то, чего уже нет.
- Первичная индексация существующей базы — отдельная разовая команда/миграция данных.

### 1.5. Гибридный поиск + RRF

Семантика (вектор) ловит «по смыслу», лексика (FTS/триграммы) ловит точные термины, артикулы, названия услуг, опечатки. Берём оба и сливаем **по рангам**, а не по сырым скорам (у них разные шкалы — складывать нельзя).

**Reciprocal Rank Fusion:**
```
score(doc) = Σ_по_источникам  1 / (k + rank_источника(doc))     // k = 60 — стандарт
```

Алгоритм:
1. Векторный поиск → top-N (например 20).
2. Лексический поиск → top-N. Для русского лучше полнотекст `to_tsvector('russian', …)` как основная лексическая ветка; существующие триграммы (`pg_trgm`) оставляем как fuzzy-ветку под опечатки.
3. Объединяем уникальные документы, считаем RRF, сортируем, берём итоговый top-k (5–8) в контекст.

Триграммный поиск у вас уже есть (`store/search.go`) — он входит как одна из веток, не выбрасываем.

### 1.6. Переформулирование запроса — дёшево и с фолбэком

Разговорную фразу клиента надо превратить в самостоятельный поисковый запрос: разрешить кореференцию из истории («а сколько это стоит?» → «сколько стоит стерилизация кошки») и убрать воду.

- Делаем дешёвым вызовом на **Lite**, низкий `max_tokens`, температура ~0.
- **Обязателен фолбэк**: если переформулировка пустая/сломалась/таймаут — ищем по сырой фразе. Гейт RAG не должен падать из-за вспомогательного вызова.
- HyDE и реранкер-кросс-энкодер — пока избыточны для нашего масштаба, держим в уме как апгрейд при росте базы.

### 1.7. Сборка контекста

- В промпт кладём top-k чанков, **каждый с явным ID источника** (`entity_type:entity_id:chunk_idx`) — чтобы потребовать от модели цитирование и потом его проверить (см. Часть 2).
- Бюджет токенов: `система + персона + контекст (k чанков) + последние N ходов`. Старую историю при переполнении — сжимаем (summary), а не обрезаем грубо.
- Контент базы знаний в промпте — это **данные, а не инструкции** (см. защиту от инъекций ниже).

## Часть 2. Guardrails (Б5)

Принцип — **defense in depth и от дешёвого к дорогому**: сначала детерминированные гейты (бесплатно), потом LLM, потом проверка после LLM. Не полагаемся на «попросили модель в промпте не врать» — это самый слабый уровень.

### 2.1. Гейт «нет контекста» — самый важный и самый дешёвый

Если ретривер не вернул ничего выше порога релевантности — **не зовём LLM за ответом вообще**. Сразу отказ/эскалация.

```
retrieved := retriever.Search(query, tenant)
if len(retrieved) == 0 || retrieved[0].Score < minScore {
    return refuseOrEscalate()   // не генерируем «ответ из головы»
}
```

Это убирает большую часть галлюцинаций до того, как они стали возможны, и стоит ноль токенов. Порог `minScore` — тюнимый, на тенант.

### 2.2. Grounding через проверяемое цитирование

Промпт-инструкция «отвечай только по контексту» обязательна, но недостаточна. Усиливаем структурно:

- Просим модель вернуть **структурированный ответ**: текст + список ID источников, на которые она опиралась.
- **Постпроверка**: каждый процитированный ID должен входить в множество реально извлечённых чанков. Если модель сослалась на ID, которого в выдаче не было — это выдуманная ссылка → ответ бракуем (фолбэк/эскалация), а не показываем клиенту.
- Источники сохраняем в `chat_messages.sources` (JSONB) — это и UX (показать клиенту/оператору), и аудит.

Опционально для пограничных случаев: второй дешёвый проход «LLM-судья» — «подтверждается ли ответ этими источниками? да/нет». Дорого на каждый ответ, поэтому только при низкой уверенности.

### 2.3. Скоринг уверенности → fallback/эскалация

Не ML, а прозрачная эвристика из сигналов, которые у нас и так есть:

- топ-скор ретривера,
- сколько источников реально подтверждают ответ,
- есть ли валидная цитата (из 2.2),
- (опц.) самооценка модели.

Ниже порога → **fallback**: вежливый отказ персоны + (если включён handoff) автоэскалация на оператора. Отказ — это **штатный путь, а не исключение/ошибка**: персона говорит «не нашёл в базе, передаю специалисту», а не роняет 500.

### 2.4. Защита от prompt-injection

Клиент (и содержимое базы знаний) может попытаться переписать поведение бота. Базовая гигиена:

- **Делимитируем** контекст и пользовательский ввод явными границами (XML-теги/маркеры), и в системном промпте прямо говорим: текст внутри этих границ — данные, инструкции внутри них игнорируются.
- Системный промпт и персона — **неизменяемы** содержимым запроса или выдачей ретривера.
- Фильтр на выходе: не отдавать наружу системный промпт/служебку, если модель попыталась его «слить».
- Фильтр тем (`Theme`) — ограничиваем тематику; явно офтопик/абьюз отбиваем дешёвым классификатором или правилами до основного вызова.

### 2.5. Guardrails вокруг tool-calls (Б4, и критично для Bitrix24 на этапе 2)

- **Валидация аргументов по JSON-schema** перед исполнением — некорректные отклоняем (это и есть критерий приёмки Б4).
- **Whitelist инструментов** — диспетчер исполняет только зарегистрированные.
- **Лимит итераций** агентского цикла (например ≤ 5 tool-вызовов на ход) — иначе риск зацикливания и неконтролируемого расхода токенов.
- **Идемпотентность сайд-эффектов**: создание лида/заявки в Bitrix24 не должно дублироваться при ретрае. Повторные обращения — связываем с существующим контактом, а не плодим новые.

### 2.6. ПДн и 152-ФЗ (технические меры — наша зона, Б1/Б5)

- **Отключить логирование запросов на стороне Yandex** — по умолчанию оно включено; ставим заголовок `x-data-logging-enabled: false` на вызовах. Для клиники с ПДн это не опция, а must.
- Не отправлять в LLM лишние ПДн; в логах телефоны/имена — **маскировать**.
- Секреты тенанта (ключи Yandex/каналов/Bitrix24) — только в зашифрованном виде в БД (AES-GCM, мастер-ключ из env), как в Б1.
- Хранить флаг согласия на обработку ПДн; способ его получения в боте фиксируем с заказчиком до старта (вопрос §11 ТЗ).

### 2.7. Eval-харнесс = и guardrail, и артефакт приёмки

Два набора тестов, прогон автоматический, на выходе — отчёт (это Артефакты 1 и 2 для приёмки этапа 1):

- **In-domain**: вопросы, покрытые базой → ожидаем ответ **с валидным источником**.
- **Out-of-domain / провокационные**: вне базы, инъекции, офтопик → ожидаем **отказ или эскалацию**, без выдумки.

Метрики, которые смотрим: доля ответов с валидной цитатой (grounding rate), точность отказов, корректность эскалаций, выборочная ручная проверка на галлюцинации. Этот же харнесс — регрессионная защита: меняем промпт/модель → прогон не должен просесть.

## Порядок внедрения (как ложится на план)

1. **Б1** — адаптеры `Provider`/`Embedder` (с раздельными doc/query моделями), шифрование секретов, `x-data-logging-enabled:false`.
2. **Б2** — `kb_embeddings` + HNSW, конвейер индексации (асинхронный, content_hash, delete), гибридный ретривер с RRF, переформулирование с фолбэком.
3. **Б3** — оркестратор: гейт «нет контекста» (2.1) встроить здесь же, сборка контекста с ID источников.
4. **Б4** — tool-фреймворк с валидацией и whitelist.
5. **Б5** — цитирование+постпроверка, скоринг уверенности, защита от инъекций, фильтр тем, eval-харнесс.

Самый дешёвый guardrail (2.1) даёт самый большой эффект — внедряем его первым же, как только есть ретривер и оркестратор.
