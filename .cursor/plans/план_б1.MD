# Б1. Фундамент: провайдер-абстракция и конфигурация тенанта

## Цель блока

Заложить backend-фундамент для «Текстовой линзы»: единый контракт LLM/эмбеддингов, адаптер YandexGPT, пер-тенантные настройки бота, шифрованное хранение секретов и CRUD API для админки. Реализация должна лечь в текущую архитектуру KnowledgeOS: `domain -> store -> service -> handler`, Chi router, GORM/PostgreSQL, tenant из JWT/`X-Company-ID`, миграции через SQL-файлы в `backend/migrations`.

## Что уже есть в проекте

- Мультитенантность: `company_id` в бизнес-сущностях, `middleware.Tenant`, `middleware.GetCompanyID`, `tenantScope(companyID)` в store.
- Роли и доступы: `superadmin/admin/editor/viewer`, `middleware.RequireRole`; админские операции сейчас доступны `admin + superadmin`.
- Backend-слои: доменные модели в `internal/domain`, репозитории/store в `internal/store`, бизнес-логика в `internal/service`, HTTP в `internal/handler`.
- Миграции: SQL-файлы применяются в лексикографическом порядке через `internal/database/migrate.go`; последняя миграция сейчас `010_user_active.sql`.
- Конфигурация: `internal/config.Config` читает env через `config.Load()`, docker-compose прокидывает env явно.
- Хранение чувствительных значений уже есть только в виде хэшей для refresh/API keys, но шифрования и обратного чтения секретов нет.

## Чего не хватает для реализации Б1

- Нет пакета `internal/llm` и общих DTO для chat messages, generation params, tool definitions, tool calls, streaming chunks и token usage.
- Нет адаптера Yandex Foundation Models: HTTP client, авторизация, chat completion, streaming, embeddings, retry/backoff, timeouts, нормализация ошибок.
- Не определены точные модели YandexGPT Lite/Pro, URI моделей, embedding-модели и формат streaming/tool-calls по актуальной документации.
- Нет `internal/crypto` для AES-GCM и нормализации мастер-ключа `SECRETS_ENCRYPTION_KEY`.
- Нет env-конфига для дефолтов Yandex и секретов: `SECRETS_ENCRYPTION_KEY`, `YANDEX_FOLDER_ID`, дефолтные model URI/endpoint/timeout/retry.
- Нет таблиц `bot_settings` и `tenant_secrets`, доменных моделей и репозиториев.
- Нет CRUD API для bot settings и секретов, а также контракта ответа, который никогда не раскрывает plaintext secret.
- Нет тестов на шифрование, tenant-isolation, RBAC настроек и отсутствие plaintext в БД.
- Нет фронтенд-формы «Настройки -> Бот»; это отдельная задача поверх backend API, но backend должен сразу выдать удобный контракт.

## Проверенные детали Yandex Cloud

Проверено через Context7 по официальному источнику `/yandex-cloud/docs`:

- Для OpenAI-compatible вызовов Yandex Cloud AI используется base URL `https://ai.api.cloud.yandex.net/v1`.
- Streaming в OpenAI-compatible API включается параметром `stream: true` на chat completions.
- Для REST/gRPC API Yandex Cloud стандартная авторизация IAM-токеном идет через заголовок `Authorization: Bearer <IAM-токен>`.
- В документации также встречается OpenAI-compatible подключение, где token передается как `api_key` SDK; для Go-адаптера это нужно явно проверить на уровне HTTP-заголовков перед реализацией.
- URI embedding-моделей строятся как `emb://<folder_id>/<model>/<version>`.
- Для генерации в workflow-примерах используется URI вида `gpt://<folder_id>/yandexgpt`.
- Официальная документация разделяет REST API генерации текста и REST API embeddings; перед кодированием адаптера нужно открыть именно API reference для точного JSON request/response, usage и ошибок.

Что Context7 не подтвердил достаточно полно:

- точный native REST endpoint генерации/streaming и embeddings;
- формат function/tool-calls в Yandex native API;
- точные model URI для Lite/Pro в целевом тарифе;
- поддерживаемый способ передачи API key сервисного аккаунта в native REST API;
- лимиты батчинга embeddings.

## Уточняющие вопросы

1. Какие именно модели должны соответствовать переключателю Lite/Pro: конкретные Yandex model URI для чата (`gpt://...`) и должны ли они храниться как enum (`lite`, `pro`) или как свободная строка `model_uri`?
2. Какой способ авторизации Yandex выбираем для tenant-секретов: IAM token, API key сервисного аккаунта, OAuth token или поддерживаем несколько вариантов?
3. Должен ли каждый tenant иметь собственный Yandex ключ, или допускается общий дефолтный ключ из env при отсутствии tenant secret?
4. В каком виде заказчик хочет хранить `SECRETS_ENCRYPTION_KEY`: base64-ключ на 32 байта, hex или обычная строка, из которой backend делает SHA-256?
5. Нужно ли разрешить admin менять LLM-секреты, или только superadmin? В текущей архитектуре admin управляет пользователями своей компании, superadmin управляет компаниями.
6. Нужен ли аудит изменения настроек/секретов уже в Б1, или достаточно `updated_at` и скрытия plaintext?
7. Какие bot-модули должны быть в `bot_settings.enabled_modules` на старте: `rag`, `channels`, `handoff`, `bitrix24`, `playground`, или пока только JSONB-заглушка?
8. Нужны ли разные настройки генерации для chat и query-rewrite/служебных LLM-вызовов, или в Б1 храним только основные `temperature/max_tokens`?
9. Должен ли endpoint проверки секрета делать реальный test-call в Yandex (`/test`) или только сохранять/удалять секрет?
10. Есть ли требования по ротации секретов: хранить несколько версий, `last_used_at`, `rotated_at`, или достаточно upsert одного секрета на `company_id + kind`?

## Архитектурные решения

### 1. Границы Б1

В Б1 реализуем инфраструктуру, а не RAG/чат-оркестратор:

- `internal/llm` описывает контракты и базовые типы.
- `internal/llm/yandex` реализует Yandex provider/embedder.
- `internal/crypto` отвечает только за шифрование/дешифрование.
- `bot_settings` и `tenant_secrets` дают storage/API для будущих Б2-Б5, каналов и Bitrix24.
- CRUD settings/secrets подключается в текущий protected router под `admin + superadmin`.

Не реализуем в Б1: pgvector, indexing, chat sessions/messages, SSE Chat API, tools registry, guardrails, frontend playground.

### 2. LLM-контракты

Создать пакет `backend/internal/llm`:

- `Provider`:
  - `Chat(ctx context.Context, req ChatRequest) (*ChatResponse, error)`
  - `ChatStream(ctx context.Context, req ChatRequest) (<-chan StreamChunk, error)`
- `Embedder`:
  - `EmbedDocs(ctx context.Context, texts []string) ([][]float32, error)`
  - `EmbedQuery(ctx context.Context, text string) ([]float32, error)`
- `Message`: `role`, `content`, опционально `tool_call_id`, `tool_calls`.
- `Tool`: `name`, `description`, `parameters` JSON Schema.
- `ToolCall`: `id`, `name`, `arguments` как `json.RawMessage`.
- `GenerationParams`: `model`, `temperature`, `max_tokens`.
- `Usage`: `prompt_tokens`, `completion_tokens`, `total_tokens`.
- `StreamChunk`: `delta`, `tool_call_delta`, `done`, `usage`, `err`.

Важно: для эмбеддингов сразу разделить `EmbedDocs` и `EmbedQuery`, потому что в плане зафиксированы разные Yandex embedding-модели для документов и запросов.

### 3. Yandex adapter

Создать `backend/internal/llm/yandex`:

- `Config`: endpoint, folder ID, API key/IAM token, default chat model, embedding doc/query model, timeout, retry count.
- Базовый endpoint по умолчанию для OpenAI-compatible API: `https://ai.api.cloud.yandex.net/v1`.
- Native REST endpoints генерации и embeddings держать отдельными config-полями, если по API reference окажется, что они нужны для tool-calls/embeddings лучше OpenAI-compatible слоя.
- `Client`: принимает `http.Client`, config и logger-free поведение; ошибки возвращает через `fmt.Errorf`, не логирует body/секреты.
- Авторизация: IAM-токен через `Authorization: Bearer <IAM-токен>` подтвержден документацией; формат API key для native REST нужно сверить отдельно.
- Для запросов с ПДн всегда ставить `x-data-logging-enabled: false`.
- Ретраить только временные ошибки: network timeout, 429, 5xx; не ретраить 400/401/403.
- Backoff: exponential + jitter, контекст должен отменять ожидание.
- Streaming реализовать так, чтобы канал закрывался всегда; ошибку финального чтения передавать через `StreamChunk{Err: err}` либо отдельный error-chunk.
- Embeddings батчить на уровне адаптера или сервиса с лимитом из документации; если Yandex endpoint фактически принимает один текст за запрос, интерфейс все равно остается batch-friendly.

Перед реализацией нужно сверить:

- endpoint URLs;
- request/response JSON для chat, stream и embeddings;
- формат tool-calls;
- формат usage/tokens;
- актуальные model URI Lite/Pro и embedding doc/query;
- ограничения по max tokens/input tokens/rate limits.

### 4. Конфигурация backend

Расширить `internal/config.Config`:

- `SecretsEncryptionKey string`
- `YandexEndpoint string` с дефолтом `https://ai.api.cloud.yandex.net/v1`
- `YandexFolderID string`
- `YandexAPIKey string` как env-fallback для локального/dev запуска; tenant secret `llm` имеет приоритет.
- `YandexDefaultChatModelLite string`
- `YandexDefaultChatModelPro string`
- `YandexEmbeddingDocModel string` как полный URI `emb://<folder_id>/<model>/<version>` или имя для сборки URI
- `YandexEmbeddingQueryModel string` как полный URI `emb://<folder_id>/<model>/<version>` или имя для сборки URI
- `YandexTimeoutSeconds int`
- `YandexMaxRetries int`

Добавить env в `.env.example`, `docker-compose.yml`, `docker-compose.staging.yml`.

Правило запуска: если endpoints Б1 создаются, но `SECRETS_ENCRYPTION_KEY` не задан/невалиден, сервис настроек секретов должен возвращать понятную ошибку на операции с секретами. Лучше валидировать на старте приложения и падать только если Б1 включен без ключа; если хотим проще и безопаснее, падать на старте при пустом ключе после добавления Б1.

### 5. Шифрование секретов

Создать `backend/internal/crypto`:

- `type Cipher struct { key []byte }`
- `NewCipher(master string) (*Cipher, error)`
- `Encrypt(plaintext []byte) (ciphertext []byte, nonce []byte, err error)`
- `Decrypt(ciphertext, nonce []byte) ([]byte, error)`

Рекомендуемый формат `SECRETS_ENCRYPTION_KEY`: base64 от 32 байт. Если нужен developer-friendly режим, можно поддержать fallback `sha256(master string)`, но это ухудшает строгость. Предпочтительно потребовать base64/32 bytes и явно документировать генерацию.

Безопасность:

- AES-256-GCM.
- nonce 12 байт из `crypto/rand`.
- ciphertext/nonce хранить как `BYTEA` в Postgres.
- Plaintext не писать в логи, ошибки, JSON-ответы и domain JSON.
- В API отдавать только metadata секрета: `kind`, `is_set`, `updated_at`.

### 6. Миграции

Добавить `backend/migrations/011_bot_settings.sql`:

- `company_id UUID PRIMARY KEY REFERENCES companies(id) ON DELETE CASCADE`
- `enabled BOOLEAN NOT NULL DEFAULT false`
- `provider TEXT NOT NULL DEFAULT 'yandex' CHECK (provider IN ('yandex'))`
- `model_tier TEXT NOT NULL DEFAULT 'lite' CHECK (model_tier IN ('lite', 'pro'))`
- `model TEXT` или `model_uri TEXT` для override после уточнения
- `temperature NUMERIC(3,2) NOT NULL DEFAULT 0.2 CHECK (temperature >= 0 AND temperature <= 2)`
- `max_tokens INT NOT NULL DEFAULT 1024 CHECK (max_tokens > 0 AND max_tokens <= 8192)`
- `persona_name TEXT NOT NULL DEFAULT 'Администратор'`
- `persona_tone TEXT NOT NULL DEFAULT 'friendly_professional'`
- `persona_rules TEXT NOT NULL DEFAULT ''`
- `enabled_modules JSONB NOT NULL DEFAULT '{}'::jsonb`
- `created_at`, `updated_at`

Добавить `UNIQUE/PRIMARY KEY company_id` и trigger/function для `updated_at`, если в проекте нет общего механизма обновления timestamps.

Добавить `backend/migrations/012_tenant_secrets.sql`:

- `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`
- `company_id UUID NOT NULL REFERENCES companies(id) ON DELETE CASCADE`
- `kind TEXT NOT NULL CHECK (kind IN ('llm','telegram','max','vk','bitrix24'))`
- `ciphertext BYTEA NOT NULL`
- `nonce BYTEA NOT NULL`
- `metadata JSONB NOT NULL DEFAULT '{}'::jsonb`
- `created_at`, `updated_at`
- `UNIQUE(company_id, kind)`
- index `idx_tenant_secrets_company`.

Не включать эти таблицы в sync-поток, пока нет явного требования синхронизировать секреты между local/cloud. Секреты лучше считать локальными к окружению.

### 7. Domain/store/service

Добавить доменные модели:

- `domain.BotSettings`
- `domain.TenantSecret`
- `domain.SecretKind`
- `domain.BotSettingsRepository`
- `domain.TenantSecretRepository`

Store:

- `BotSettingsStore.Get(ctx, companyID)`
- `BotSettingsStore.Upsert(ctx, companyID, settings)`
- `TenantSecretStore.GetMetadata(ctx, companyID, kind)`
- `TenantSecretStore.GetEncrypted(ctx, companyID, kind)`
- `TenantSecretStore.Upsert(ctx, companyID, secret)`
- `TenantSecretStore.Delete(ctx, companyID, kind)`

Service:

- `BotSettingsService.Get(ctx, companyID)` возвращает settings или дефолтный объект, если строки еще нет.
- `BotSettingsService.Update(ctx, actor, req)` валидирует RBAC, model tier, temperature, max tokens, JSON модулей.
- `TenantSecretService.Set(ctx, actor, kind, plaintext, metadata)` шифрует и upsert-ит.
- `TenantSecretService.GetPlaintext(ctx, companyID, kind)` используется только внутренними провайдерами, не handler-ами.
- `TenantSecretService.Delete(ctx, actor, kind)`.
- `TenantSecretService.ListStatus(ctx, companyID)` возвращает `is_set` по поддержанным kind.

RBAC:

- Читать настройки: `admin + superadmin`; для будущего playground можно отдельно дать read editor, но не в Б1.
- Обновлять настройки/секреты: минимум `admin + superadmin`.
- Superadmin через текущий `X-Company-ID` сможет работать с выбранным tenant.

### 8. HTTP API

Добавить `backend/internal/handler/bot_settings.go` или `bot.go`:

- `GET /api/v1/admin/bot/settings`
- `PUT /api/v1/admin/bot/settings`
- `GET /api/v1/admin/bot/secrets`
- `PUT /api/v1/admin/bot/secrets/{kind}`
- `DELETE /api/v1/admin/bot/secrets/{kind}`
- опционально `POST /api/v1/admin/bot/llm/test` после согласования.

Формат `PUT /settings`:

```json
{
  "enabled": true,
  "provider": "yandex",
  "model_tier": "lite",
  "model": null,
  "temperature": 0.2,
  "max_tokens": 1024,
  "persona_name": "Администратор",
  "persona_tone": "friendly_professional",
  "persona_rules": "",
  "enabled_modules": {
    "rag": true,
    "handoff": false
  }
}
```

Формат `PUT /secrets/{kind}`:

```json
{
  "value": "plaintext-secret",
  "metadata": {
    "auth_type": "api_key"
  }
}
```

Формат ответа по секретам:

```json
{
  "kind": "llm",
  "is_set": true,
  "metadata": {
    "auth_type": "api_key"
  },
  "updated_at": "2026-06-24T00:00:00Z"
}
```

`value` никогда не возвращать.

### 9. Wiring в `cmd/api/main.go` и router

В `cmd/api/main.go`:

- создать crypto cipher из config;
- создать `BotSettingsStore`, `TenantSecretStore`;
- создать `BotSettingsService`, `TenantSecretService`;
- создать handler и добавить в `handler.Handlers`.

В `handler/router.go`:

- расширить `Handlers` полем `Bot`;
- добавить routes внутри protected JWT+Tenant group;
- обернуть routes в `RequireRole(domain.RoleAdmin, domain.RoleSuperadmin)`.

Yandex provider можно не поднимать как singleton для всех tenant, если secret tenant-specific. Лучше сделать фабрику:

- `LLMFactory` получает config defaults + secret service + settings service.
- `ForCompany(ctx, companyID)` читает settings и llm secret, возвращает `llm.Provider`/`Embedder`.

Так Б2-Б3 смогут получать провайдера по tenant без протаскивания HTTP/crypto деталей.

### 10. Тесты

Unit:

- `internal/crypto`: encrypt/decrypt, разные nonce, неверный ключ не дешифрует, пустой plaintext допустим/недопустим по решению.
- `internal/llm/yandex`: mock `httptest.Server`, headers auth + `x-data-logging-enabled:false`, retry на 429/5xx, no retry на 400/401, parse usage/tool calls/embeddings.
- `service.BotSettingsService`: дефолт при отсутствии строки, валидация temperature/max_tokens/model_tier.
- `service.TenantSecretService`: plaintext не возвращается в status, ciphertext отличается от plaintext, tenant isolation.

Integration/API:

- admin может `GET/PUT settings`.
- viewer/editor не может менять settings/secrets.
- superadmin с `X-Company-ID` меняет настройки выбранной компании.
- `PUT secret` -> в БД нет plaintext -> `GET secrets` возвращает только status.
- `DELETE secret` сбрасывает `is_set`.

## Риски и замечания

- Главный риск Б1 - неверно заложить Yandex DTO без сверки с текущей документацией; это нужно сделать до кодинга адаптера.
- Нельзя логировать request/response body LLM-вызовов, потому что там могут быть ПДн и секреты.
- Секреты не должны участвовать в существующем sync/export без отдельного решения: перенос tenant secret между окружениями может быть небезопасен и зависит от мастер-ключа.
- Если `SECRETS_ENCRYPTION_KEY` потерян или изменен, существующие секреты станут недешифруемыми; нужен документированный порядок ротации/backup.
- `bot_settings` one-to-one с company лучше создавать lazy на первом `GET/PUT`, чтобы не усложнять bootstrap и создание компаний.
- Streaming и tool-calls лучше включить в интерфейс сразу, даже если первый consumer появится в Б3/Б4.
